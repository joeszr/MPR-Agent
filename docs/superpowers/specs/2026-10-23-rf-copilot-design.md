# 面向西安大厂的通信 × AI 项目改造方案：RF Copilot

更新：2026-10-23。对象：北邮信通硕士、2028 届；主投 AI 应用／后端研发，通信作为领域特色。

## 1. 先给结论

把当前 `MPR_python` 改造成 **RF Copilot：基于 RAG 与工具调用的无线射频仿真诊断平台**。

它面向无线研发／测试工程师，完成“查规范 → 配参数 → 提交仿真 → 查看指标 → 对比实验 → 生成带证据的诊断报告”。你的竞争力是能把真实通信计算包装成可靠的软件服务，并让 Agent 正确使用它。

主线技术栈：**Python、FastAPI、Pydantic、PostgreSQL、Redis、Celery、Qdrant、BM25、Embedding／Reranker、LangGraph、LLM Function Calling、Docker Compose、pytest**。保留 C++ 作为笔试与基础能力，PyTorch 用于理解模型与可选实验。

这里的技术选择是方案建议，并非每家公司 JD 都要求这一整套。完成后才能写“实现／使用”，现在不能写“熟练掌握”或编造性能提升。

## 6. 产品闭环与架构

典型场景：“对比 FR1、100 MHz、30 kHz SCS 下两个 RB 分配的 ACLR／EVM，指出哪个限制了输出功率，并说明采用的实验阈值与规范出处。”

系统先验证参数和规范版本，再检索资料、提交有限规模仿真，最后引用结构化实验结果与条款生成报告。无法确定标准适用范围时应说明缺失条件；知识库不足时不能编造条款。

架构顺序：**Streamlit 演示界面 → FastAPI → 有界 Agent 工作流 → 检索工具／任务工具 → Celery worker → 仿真核心**。

- PostgreSQL：任务、实验参数、状态、结果索引、工具调用轨迹。它是任务状态事实来源。
- Redis：Celery broker 与可丢失缓存；不作为实验结果唯一存储。
- Qdrant：规范段落向量与元数据；BM25 索引提供术语精确召回。
- 文件目录：小型图表、NPZ 与报告；数据库保存路径及哈希，不把大数组塞进 Redis。
- 付费 LLM API：理解意图、选择工具、组织有引用的解释。仿真结论与计算值来自代码。

初版只支持一个开发者／演示用户，不宣称多租户生产系统。服务只监听本机或受控开发网络，不把无鉴权演示实例公开发布。

### 6.1 仿真核心与契约

先支持一个固定、经过验证的 FR1 参数档：100 MHz、30 kHz SCS、NRB=273；CP-OFDM 为主，DFT-s-OFDM 在兼容层回归，不同时开放所有标准组合。

输入至少包括：`waveform`、`profile_id`、`rb_start`、`rb_count`、`mod_order`、`pa_model`、`seed`、`trials`、`threshold_profile_id`、`engine_version`。服务验证 RB 不越界、模型已实现、调制合法、波形支持，禁止随意组合 Fs／FFT／SCS。

输出包含：`status`、配置和种子、功率口径、每次试验结果、EVM／ACLR 测量值、检查状态、阈值、终止原因、运行时间、版本。SEM 初版可保留 pass／fail，IBE 关闭时明确 `not_evaluated`。

`pass`、`fail`、`not_evaluated`、`skipped`、`error` 分开；NaN／Inf 不直接输出为非标准 JSON。没有参考功率时 `mpr_db=null`，报告说明原因。

不能直接把“搜索停止点失败指标”当作“最后有效功率处指标”。最终结果必须重新测量／保存同一工作点下的功率与指标。

### 6.2 RAG：围绕“标准条件”做检索

第一版语料约 30—60 个经人工校验的段落／表格块，来自获准使用的标准摘录、项目说明、实验阈值说明。先把有限资料做对，再扩容。

1. 按章节、条款、表格边界切分，保留表头、单位和脚注；初始每块约 300—700 中文字或对应英文长度，允许约 80 字重叠，按评测调整。
2. 每块保存 `document_id/version/release/clause/page/section/band/duplex/power_class/source_url/content_hash`；未知字段为空，不猜测。
3. BGE-M3 作为初始 embedding 候选，BGE reranker 作为候选重排器；实施时核对模型卡、许可证、资源需求，固定模型 revision。本地不足可 CPU 小批处理，不依赖生成大模型本地部署。
4. dense 和 BM25 各取 20 条，在同一版本／适用范围内做 RRF 融合，候选前 20 条重排，最终给模型 5 条。小语料下比较是否真有收益，允许保留更简单的配置。
5. 明确版本时先过滤；未明确版本且存在冲突时返回澄清，不能把多个 Release 的阈值拼接成一个答案。
6. 回答返回条款、版本、来源与实际支持的主张；相关性低或证据不支持就拒答，阈值只用开发集校准。

[Qdrant 官方过滤文档](https://qdrant.tech/documentation/search/filtering/)支持按 payload 条件过滤；它在此用于版本与适用范围约束。向量库不是标准真相来源，仍需人工核对语料。

标准来源入口可使用 [3GPP 规范归档](https://www.3gpp.org/ftp/Specs/archive/38_series/38.101-1/)；本次访问返回 403，尚未读取具体规范正文，因此本文不新增“已核实的标准阈值”。实施时使用自己合法持有的版本或其他官方可访问分发，记录版本与文件哈希；区分 UE 与基站规范，不能混引。

### 6.3 Agent：一个可控工作流，四个工具

使用 LangGraph 表达 `解析 → 验证 → 检索／提交任务 → 查询结果 → 生成报告`，而不是多角色无限对话。[官方概述](https://docs.langchain.com/oss/python/langgraph/overview)说明它适合显式工作流编排；框架选择本身不是成果。

工具：`search_knowledge(query, filters)`、`submit_simulation(config)`、`get_experiment(job_id)`、`compare_experiments(job_ids)`。不提供任意 Python／Shell 执行。

上限：每次会话 6 次工具调用、最多提交 2 个实验；每实验最多 2 个 RB 配置、每配置最多 3 次试验；工作进程任务硬时限 120 秒，LLM 单次请求 30 秒，瞬态 API 错误最多重试 1 次。以上是初始工程预算，先小样本实测，再在配置和文档中同步调整。

长任务返回 job_id，不占着 HTTP 连接等全量扫描。完成后再次查询生成报告。检索文档和工具输出视为数据，文档中的“忽略规则／运行命令”不能触发工具。

### 6.4 后端：让 Redis 等组件有实际用途

- `POST /v1/experiments` 返回 202 + job_id；`GET /v1/experiments/{id}` 返回状态与结果；`POST /v1/questions` 返回引用、文本、工具轨迹或待查询任务。
- 状态机：`queued → running → succeeded/failed/timed_out`；参数校验失败返回 422，不进入队列。
- 幂等：规范化参数、种子、代码版本、阈值版本一起算哈希，PostgreSQL 唯一约束防重复。重复请求返回原 job_id。
- 队列投递失败保留 queued 状态与错误，提供补投扫描；worker 以数据库条件更新领取任务。重复投递不重复写结果。超时／崩溃任务通过超时扫描标记，不依赖 Redis 锁实现“恰好一次”。
- Redis 结果缓存 TTL 24 小时，只缓存 succeeded；读缓存失败回源 PostgreSQL。变更代码或阈值必须换 key。检索缓存 TTL 1 小时，key 包含语料、embedding 和 reranker 版本。
- Redis 同时用于 broker 时，缓存降级不代表还能提交新任务；提交保留 queued 并说明暂缓调度。部署至少区分 key 前缀并设置容量，进一步隔离实例放到后续。
- CPU 仿真进程独立运行；`async def` 不会把 NumPy 重计算自动变成非阻塞任务。
- 记录 request_id、job_id、耗时、工具次数、token 用量、失败原因；日志不写 API key。

[Redis 官方 keyspace 文档](https://redis.io/docs/latest/develop/use/keyspace/)可作为 TTL 学习入口。数据库事务、幂等、重试和一致性比仅能启动 Redis 更值得写入项目经历。

## 10. 评测：拿什么证明做过

以下数字是验收目标，不是现有成果，未达标也要如实报告。

### 通信计算

固定 12 个小样本配置作为回归集，覆盖 RB 两端／中间、不同占用、合法与非法配置、无有效工作点、跳过、未检测指标。浮点对照先取绝对容差 1e-6／相对容差 1e-5，再依据数值分析调整。旧结果一致只证明兼容，不证明规范正确；修复缺陷时新增独立解析／人工复核样例。

### 检索与生成

人工整理 60 个问题：30 个开发、30 个冻结测试；按问题模板／意图分组切分避免改写泄漏。测试集含 18 个可答、6 个缺少适用条件／版本冲突、6 个无答案问题。每题列必要证据、允许答案和应澄清条件。

对 18 个可答问题报告 Recall@5（目标 ≥0.85）；逐条事实检查引用支持率（目标 ≥0.90）；无答案的 6 题目标至少 5 题正确拒答。小样本同时给分子／分母，不宣传广泛泛化。比较 dense、BM25、混合、混合+重排四组；其他参数一致。不要只用 LLM 给自己打分。

### Agent 与系统

固定 20 个场景，覆盖问答、仿真、对比、非法参数、证据冲突、超时、API 错误、提示注入；成功场景要求工具与答案都正确，目标至少 16/20。所有危险或越界输入必须在执行前被阻止。

用固定 50 次请求、并发 1／4／8 测提交接口和查询接口；分别报告冷／热缓存、排队、计算、LLM 和总耗时，记录 CPU、内存、模型版本。不得用缓存命中耗时宣传真实仿真速度，也不宣称该样本证明高并发生产能力。

## 12. 简历写法与面试准备

项目名称：**RF Copilot：面向无线射频实验的 RAG 与 Agent 仿真诊断平台**。

完成后可用以下模板，方括号必须用真实测量替换，尚未做的模块直接删掉：

1. 将 CP-OFDM／功放仿真封装为 FastAPI 工具服务，设计结构化参数、种子与版本追踪，实现 EVM／ACLR 等指标的实验查询和对比。
2. 构建带标准版本过滤的通信知识库，采用 BM25 + 向量检索与重排，在 [N] 道冻结问题上取得 Recall@5 [X]、引用支持率 [Y]，提供证据不足拒答。
3. 基于 LangGraph 实现有界工具工作流，结合 PostgreSQL、Celery 与 Redis 支持长任务、重复请求幂等和缓存失效，在 [N] 个端到端场景中通过 [M] 个。

AI 应用岗位先讲检索、评测、工具可靠性；后端岗位先讲任务状态、事务、幂等、缓存和性能。两个版本共享真实项目，不伪造不同业务经历。

必须能回答：为什么用 Agent；固定工作流是否更简单；BM25 为什么能补 dense；如何避免混用标准版本；引用存在为什么不代表支持结论；TTL 到期与版本失效有什么区别；worker 重复投递怎么办；数据库成功而入队失败怎么办；CPU 仿真为什么不能堵住 API；为什么这个结果不能直接叫 MPR；没有测 IBE 为什么不能判全通过；项目到底提升了哪个环节、在哪些条件下无效。

## 13. 可选扩展与资源控制

**只选一项**，且不得挤占核心验收：

- 外部 3090：选实际能放下的开源指令模型，比较 API 与本地服务的工具成功率、延迟、显存和成本；模型尺寸、上下文、量化与并发须实测，不能说“3090 必然跑得动某模型”。
- C++／pybind11：profiling 确认瓶颈后只改一个热点，与 NumPy 基线比较数值误差和端到端收益；不为了使用 C++ 重写 FFT。
- 小型代理模型：从已校验的仿真生成数据，用树模型与 PyTorch MLP 对比预测功率／裕量。按 RB 区域或 PA 模型分组留出，避免随机拆分邻近样本泄漏；预测仅用于候选排序，最终结论仍由仿真复核。没有可靠标签时不启动。

API 费用先记录真实 token 与单价，设置可配置月限额，默认建议 100 元作为开发控制值，可按个人预算调整；mock／录制响应负责大部分回归测试。外部 GPU 只在专门实验时租用，完成立即释放，不把服务器常驻费作为项目必要条件。
